# Chat API

Procyon chat REST API reference.

> **Status:** Implementation-based documentation, updated 2026-10-30. Derived from the route handlers discussed during the refactor; confirm against the current source before deployment.

## Overview

- **Base URL:** `/api/chat/rooms`
- **Authentication:** Existing NextAuth browser session cookie. All routes require login.
- **Authorization:** Room upsert and all message deletion operations require an administrator (`getUserv2().admin === true`).
- **Media type:** `application/json` for request bodies and responses.
- **Runtime:** Next.js App Router Route Handlers. Dynamic `params` are asynchronous in Next.js 16 (`const { id } = await params`).
- **Time zone:** `Asia/Seoul` (KST, UTC+09:00).

Successful responses follow `{ "ok": true, "data": ... }`; error responses follow `{ "ok": false, "error": "..." }`. The API uses HTTP status codes in addition to the `ok` field.

## Endpoints

| Method | Path | Required role | Description |
| --- | --- | --- | --- |
| GET | `/api/chat/rooms` | Logged-in user | List chat rooms |
| POST | `/api/chat/rooms` | Administrator | Create or update a chat room |
| GET | `/api/chat/rooms/{id}` | Logged-in user | Read room metadata |
| GET | `/api/chat/rooms/{id}/messages` | Logged-in user | Read paginated messages |
| POST | `/api/chat/rooms/{id}/messages` | Logged-in user | Send a message |
| DELETE | `/api/chat/rooms/{id}/messages?from=...&to=...` | Administrator | Delete messages in a time interval |
| DELETE | `/api/chat/rooms/{id}/messages/all` | Administrator | Clear messages without removing the room |
| DELETE | `/api/chat/rooms/{id}/messages/{messageId}` | Administrator | Delete one message |

`id` is a room ID matching `^[a-zA-Z0-9_-]{1,50}$`. `{messageId}` is a Firestore message document ID (nonempty, no `/`, at most 256 characters); `all` is reserved as a route segment.

## Data shapes

### Chat room

```json
{
  "id": "general",
  "roomName": "General",
  "createdAt": "2026-10-30 13:00:00.000",
  "updatedAt": "2026-10-30 14:00:00.000",
  "lastMessage": "Hello",
  "lastMessageSenderName": "Example Name",
  "lastMessageCreatedAt": "2026-10-30 14:00:00.000"
}
```

The metadata fields `lastMessage`, `lastMessageSenderName`, and `lastMessageCreatedAt` may be absent in older rooms; `lastMessageCreatedAt` may be `null`. The current implementation can expose other stored room-document fields, including internal deletion state. The example is illustrative, not a strict whitelist of response properties.

### Anonymized message

```json
{
  "version": "v1",
  "id": "exampleMessageId",
  "text": "Hello",
  "createdAt": "2026-10-30 14:00:00.000",
  "sender": {
    "hash": "example-hmac-hash",
    "nickname": "Anonymous nickname",
    "major": "Computer Science"
  }
}
```

The `sender` object in message GET/POST responses is generated by `anonymizeChat()`. The raw sender email and name are not returned in those responses. Room metadata is **not** anonymized by the current route handlers; in particular, `lastMessageSenderName` may contain a real name.

## Routes

### GET `/api/chat/rooms`

Returns chat rooms ordered by `updatedAt` descending according to the Repository.

**Response — `200 OK`**

```json
{
  "ok": true,
  "data": [
    { "id": "general", "roomName": "General", "createdAt": "2026-10-30 13:00:00.000", "updatedAt": "2026-10-30 14:00:00.000" }
  ]
}
```

### POST `/api/chat/rooms`

Administrator-only room upsert. If `roomId` exists, updates its fields; otherwise creates it.

**Request**

```json
{ "roomId": "general", "roomName": "General" }
```

`roomId` is required. `roomName` is optional in the current Service (defaults to `roomId`). The current upsert contract accepts other room fields; avoid sending arbitrary properties from untrusted clients.

**Response — `200 OK`**

```json
{
  "ok": true,
  "data": { "id": "general", "roomName": "General", "createdAt": "2026-10-30 13:00:00.000", "updatedAt": "2026-10-30 14:00:00.000" }
}
```

This endpoint currently returns `200` for both creation and update, not `201`.

### GET `/api/chat/rooms/{id}`

Returns one room, or `404` if not found.

**Response — `200 OK`**

```json
{ "ok": true, "data": { "id": "general", "roomName": "General", "createdAt": "2026-10-30 13:00:00.000", "updatedAt": "2026-10-30 14:00:00.000" } }
```

### GET `/api/chat/rooms/{id}/messages`

Fetches recent, older, or newer messages. Messages are always returned in ascending order of `(createdAt, messageId)`.

| Query parameter | Type | Description |
| --- | --- | --- |
| `before` | string | Opaque composite cursor; fetch strictly older messages |
| `after` | string | Opaque composite cursor; fetch strictly newer messages |
| `limit` | integer | Number of messages, between 1 and 100; defaults to the Repository's configured recent limit, capped at 100 |

`before` and `after` cannot be specified together. A cursor is Base64URL-encoded `{ "createdAt": "YYYY-MM-DD HH:mm:ss.SSS", "id": "..." }`, but clients must treat it as opaque and forward the value returned by the server. The old timestamp-only cursor is **not** compatible.

**Example**

```http
GET /api/chat/rooms/general/messages?limit=50
GET /api/chat/rooms/general/messages?before=<oldest-cursor>&limit=50
GET /api/chat/rooms/general/messages?after=<latest-cursor>&limit=50
```

**Response — `200 OK`**

```json
{
  "ok": true,
  "data": {
    "roomId": "general",
    "messages": [
      {
        "version": "v1",
        "id": "exampleMessageId",
        "text": "Hello",
        "createdAt": "2026-10-30 14:00:00.000",
        "sender": { "hash": "example-hmac-hash", "nickname": "Anonymous nickname", "major": "Computer Science" }
      }
    ],
    "direction": "recent",
    "cursor": { "oldest": "<opaque-cursor>", "latest": "<opaque-cursor>" },
    "hasMessages": true,
    "hasMore": false
  }
}
```

`direction` is `recent`, `before`, or `after`. `cursor.oldest` and `cursor.latest` correspond to the first and last returned message, or `null` for an empty page. `hasMore` refers to the selected query direction; it does not certify that no messages exist in the other direction.

**Client pagination rules:** Use `cursor.oldest` when loading history and `cursor.latest` when polling for newer messages. When a response is empty, retain the previously known cursor rather than resetting it to `null`. If an `after` request has `hasMore: true`, keep fetching using the new latest cursor until caught up.

### POST `/api/chat/rooms/{id}/messages`

Creates a message in the specified room.

**Request**

```json
{ "text": "Hello" }
```

`text` must be a nonempty string of at most 5,000 JavaScript string code units under the current Service validation. The server constructs `sender` from `getUserv2()` (`email`, `name`, `major`). Client-provided `sender` values are ignored.

**Response — `201 Created`**

```json
{
  "ok": true,
  "data": {
    "version": "v1",
    "id": "exampleMessageId",
    "text": "Hello",
    "createdAt": "2026-10-30 14:00:00.000",
    "sender": { "hash": "example-hmac-hash", "nickname": "Anonymous nickname", "major": "Computer Science" }
  }
}
```

Note that `data` is the message itself, **not** `{ "message": ... }`.

### DELETE `/api/chat/rooms/{id}/messages?from=...&to=...`

Administrator-only deletion in the half-open time interval **`[from, to)`**, inclusive of `from` and exclusive of `to`.

Both query parameters are mandatory, must use `YYYY-MM-DD HH:mm:ss.SSS` in KST, and must satisfy `from < to`. Missing parameters do not trigger a full clear. URL-encode spaces and other special characters.

**Example**

```http
DELETE /api/chat/rooms/general/messages?from=2026-10-30%2013%3A00%3A00.000&to=2026-10-30%2014%3A00%3A00.000
```

**Response — `200 OK`**

```json
{ "ok": true, "data": { "deletedCount": 42 } }
```

### DELETE `/api/chat/rooms/{id}/messages/all`

Administrator-only clear of all messages in a room. **The room document remains.**

**Response — `200 OK`**

```json
{ "ok": true, "data": { "deletedCount": 42 } }
```

### DELETE `/api/chat/rooms/{id}/messages/{messageId}`

Administrator-only single-message deletion. A missing message results in `404` according to the Service's `MessageNotFoundError` contract.

**Response — `200 OK`**

```json
{ "ok": true, "data": { "deletedCount": 1 } }
```

## Errors

| HTTP status | Meaning | Typical cause |
| --- | --- | --- |
| `400 Bad Request` | Invalid input | Invalid room ID, cursor, time range, message body, or limit |
| `401 Unauthorized` | Not logged in | Missing/invalid session |
| `403 Forbidden` | Insufficient privileges | Non-admin attempts a protected operation |
| `404 Not Found` | Resource missing | Room not found, or message not found for single deletion |
| `409 Conflict` | Concurrent deletion in progress | `RoomDeletingError` during a write/delete |
| `500 Internal Server Error` | Unexpected server error | Unhandled database or application failure |

**Error example**

```json
{ "ok": false, "error": "Administrator permission required" }
```

The implementation currently returns human-readable error messages rather than stable machine-readable error codes. Do not depend on exact error strings in client logic.

## Operational notes

- Firestore is the persistent source of truth. The Repository uses Redis for room metadata and recent-message cache, falling back to Firestore where necessary.
- Historical pagination generally uses Firestore, while recent-message and `after` queries may use Redis when the cached range is complete.
- Bulk deletion runs in batches, so deletion is **not atomic across all batches**. The Repository uses a room-level deletion marker to reject concurrent writes; interrupted deletions may need administrator recovery.
- The current polling API returns new messages, not deletion events. An already displayed message removed by an administrator may remain in a browser until the client reloads or implements reconciliation.
- The current room response can include raw room metadata such as `lastMessageSenderName` and `_messageDeletion`. Review these fields before treating room responses as privacy-safe.
- The current Repository cache implementation requires concurrency and Redis-failure testing; TTL or generation values alone do not guarantee strong consistency.
- No room-deletion API is documented because the current Route Handlers do not expose one.

## Browser example

Run the following in the developer console of an authenticated page:

```js
const base = "/api/chat/rooms/general/messages";
const response = await fetch(`${base}?limit=20`, { cache: "no-store" });
const result = await response.json();
if (!response.ok || !result.ok) throw new Error(result.error || "Request failed");
console.log(result.data.messages, result.data.cursor);
```
